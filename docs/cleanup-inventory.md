# 复用测试机前的只读盘点

当前只实现盘点，没有卸载器，没有删除计划执行开关。
此前成功的手工测试节点保持不变；本文不是卸载授权，也不是“已经清理完成”的记录。

## 使用方式

代码交付至选定的测试 VPS 后，在 root 会话的项目目录运行：

```bash
python3 -m snellctl cleanup-plan
python3 -m snellctl cleanup-plan --json
```

两条命令任选其一；普通中文菜单的 6 也是同一个只读入口。
没有 `--apply`、`--yes`、`--root` 或凭据参数。不请求 sudo，不自动保存报告。
先按 [源码交付说明](source-delivery.md) 取得代码，不能直接在尚未收到代码的 VPS 上运行这些命令。
现有 Mac 开发机只会报告平台不支持，不会探测远端 VPS。

此盘点可识别 Debian 12/13 的 amd64/arm64 环境，**不表示安装器已支持 Debian 12 或 ARM64**。
实验安装首轮仍限定 Debian 13 / amd64。清理盘点固定为 `main`，不推断其他节点可删除。

## 报告能说明什么

- 软件包、IPv4/IPv6 监听角色及实际端口、UFW 状态和默认入出站策略，复用 `doctor` 的有限检查。
- 固定名称的节点服务、Nginx、Certbot、UFW、SSH 的有限状态属性；不获取服务启动参数。
- main 的约定配置、服务、程序、钩子和凭据路径是否存在，以及文件类型、权限等元数据。
- 固定共享目录的直属条目数；非约定名称只计数，不输出域名或其他文件名，不递归打开。
- 如果存在安装器记录，读取脱敏阶段状态；损坏、无法安全访问或忙碌的记录标为未知。

节点密码、CF Token、证书私钥、Nginx 站点和 unit 内容都不读取。
运行记录只读固定 JSON，不执行其内容或追踪其中的路径。不会调用 Nginx、Certbot 或节点二进制。
不会发起 DNS、Cloudflare、ACME 或其他外部网络请求。
检查只读元数据和状态；操作系统自身的访问时间更新不属于配置修改。

`systemctl show` 仅请求白名单状态属性，输出值再次按枚举过滤；其他属性及原始错误不复制到报告。
这是基于 [systemctl 的属性查询接口](https://manpages.debian.org/trixie/systemd/systemctl.1.en.html) 实现的有限查询，
不是完整依赖分析或运行安全审计。

## 归属与共享边界

手工测试机虽然使用了 `/etc/snellctl`、`/opt/snellctl` 和相同的服务名，
但没有新安装器的完整归属记录。报告会标为“没有安装器记录，不能自动认领”。
不能为了通过检测而补造记录，也不能把手工部署冒充为自动安装验收。

即使有阶段完成记录，本命令也没有比对内容摘要，不证明文件仍由工具独占。
目录中只有一张证书、一份凭据或一个程序版本，也不证明没有其他地方引用它们。
`known_names` 只表示名称与约定相同；`other_names` 也不等于一定属于其他业务。

报告按以下用途分类，而非生成可删除清单：

| 类别 | 当前处理原则 |
| --- | --- |
| 节点配置和两个专用服务 | 待确认实际内容、引用和归属，不自动认领或删除 |
| Nginx 站点、钩子、凭据、程序版本、Certbot 覆盖 | 可能共享，未完成引用检查前保留 |
| 安装状态、锁、启动保护和 mask 路径 | 未完成操作需先核查；不为“干净”而直接移除 |
| SSH、UFW、全部现有规则、内核、软件源、无关业务 | 本步骤全部保留，不重置、不卸载、不自动清理依赖 |

符号链接不跟随，异常文件类型/权限、超出目录计数上限及无法查询的状态都会提示核查。
部分 systemd mask 或 override 链接可能本来合法；提示核查不代表已确认故障。
Nginx 自定义 include、容器、非标准服务/节点路径、其他计划任务及云防火墙没有完整覆盖。
报告是非原子快照，不排除并发改动；实际清理前仍需重新检查。

## 后续清理需要的单独确认

1. 选定确切 VPS，确认可用的服务商恢复控制台和 SSH 新连接；先完成只读盘点。
2. 针对发现的资源补查实际引用，确认哪些是原手工项目专用、哪些共享。
3. 将节点停止/删除、指定站点/证书/钩子/凭据处理、指定 UFW 入口规则处理分别列明，获得用户确认。
4. 软件包移除单独审查依赖影响；不能为满足安装器的新机检查而删掉共享业务。
5. 完成获授权清理后重新检查 SSH/UFW、监听、续期及残留，再决定是否允许实验安装。

证书清理应先处理实际引用，再通过 Certbot 的指定证书删除功能，不能直接删除整个
`/etc/letsencrypt`。本地删除不等于吊销；是否吊销是另一项决定。
参见 [Certbot 删除证书说明](https://eff-certbot.readthedocs.io/en/stable/using.html#deleting-certificates)。
本步骤不运行任何删除或吊销命令，也不读取 Cloudflare Token 或联系其 API。

## 状态和测试边界

- 退出码 `0`：此次有限盘点收集完成，**不是允许卸载、系统安全或已恢复新机**。
- 退出码 `1`：有未知、计数受限或文件元数据需核查项，保留现场。
- 退出码 `2`：不支持的环境或非 root；不自动提权。
- 所有报告的 `cleanup_authorized` 始终为 `false`。

本地测试使用临时目录和模拟服务输出，验证没有配置写入、没有系统修改命令、
不读取秘密文件、手工安装不自动认领、路径替换/损坏/忙碌处理和报告脱敏。
尚未在实际 VPS 运行新盘点器，也未执行任何真实卸载。
